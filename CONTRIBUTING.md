# Contributing to patchwork

Thanks for contributing! Here's a quick little guide about how to build and
how patchwork is laid out

## Building

Patchwork has an official `flake.nix`. If you're using nix just use `nix develop`
to enter the development shell.
For non-nix users, you need Rust 1.95 or newer. The app also needs Tauri's system libraries
([list](https://tauri.app/start/prerequisites/)).

```sh
cargo run -p patchwork-cli -- --help    # the CLI
cargo run -p patchwork-gui              # the app
```

To test things without touching your real mods and games, point
`PATCHWORK_HOME` at a scratch directory.

## Checks

CI runs these, and PRs need to pass them:

```sh
cargo fmt --all --check
cargo clippy --workspace --all-targets --locked -- -D warnings
cargo test --workspace --locked
for f in crates/patchwork-gui/ui/*.js; do node --check "$f"; done
```

## How it fits together

Mods come from **sources**, are pinned in a profile's **lockfile**, are
stored by hash in the **content store**, and are put in the game by a
**deployer**. Sources and deployers only *describe* what to fetch and where
files go; core does all the file I/O. That keeps them easy to test, and
ready to run sandboxed later.

Where each piece of state lives on disk is in
[docs/design/state.md](docs/design/state.md).

| Crate | |
|---|---|
| `patchwork-core` | registry, profiles, lockfiles, store, deploy engine, and every trait (`Source`, `Deployer`, `ProfileFormat`, `Runner`, and the extension hooks). No networking |
| `patchwork-sources` | `local`, `url`, `nexus`, `thunderstore`, `modrinth` |
| `patchwork-deployers` | deployers that aren't about one game (`rules`, data-driven) |
| `patchwork-bethesda` | Bethesda games: the deployer, load order, plugin limit and FOMOD installers |
| `patchwork-smf` | HITMAN World of Assassination, with Simple Mod Framework mods |
| `patchwork-formats` | profile import and export (patchwork zip, r2modman, link lists) |
| `patchwork-builtin` | registers the bundled extensions; `bethesda` and `smf` are features |
| `patchwork-sync` | iroh peer-to-peer sync and the background daemon |
| `patchwork-cli` | the `patchwork` command, a thin layer over core |
| `patchwork-gui` | the app (Tauri). Its UI is plain JS modules in `ui/`, with no bundler or npm |
| `registry-gen` | dev tool that regenerates `registry/` from Thunderstore |

`vendor/quickentity-rs` is a vendored copy used by the SMF deployer.

## Adding a game

Most games need only a TOML file in `registry/games/`; see
[registry/README.md](registry/README.md). Set
`PATCHWORK_REGISTRY_PATH=$PWD/registry` to load your changes without
rebuilding.

If a game needs behaviour that data can't describe, such as a load order,
an installer format, or a check before deploying, write an **extension**
rather than special-casing it in core, the CLI or the GUI.
[docs/design/extensions.md](docs/design/extensions.md) has the hooks and
the rules for them. If you change what's built, keep its "Order of work"
section up to date.

## Conventions

- Keep trait inputs and outputs serializable. `Deployer::build` writes only
  into its `out` directory.
- The `--pw-*` CSS variables and the ids and classes in `ui/index.html` are
  public API for user themes. If you rename one, say so in the release
  notes.
- patchwork is MIT-licensed. Ask before adding a copyleft dependency
  (GPL, LGPL, ...).

## Releasing

1. Bump `version` in `Cargo.toml`, add a `## <version>` section to
   `CHANGELOG.md`, and push them to main. That section becomes the GitHub
   release's notes and what the app's update dialog shows; a dry run's plan
   output has it as `announcement_changelog` if dist found it.
2. In GitHub's Actions tab, run the **Release** workflow on main with the
   tag to make (e.g. `v0.2.0`).

`release.yml` builds the CLI with dist, the app's bundles in the same jobs,
and then the `latest.json` the app's updater reads. The GitHub Release (and
its tag) is only created once everything has built. If any job fails there's
no release, so fix the problem and re-run the failed jobs.

Running it with the default tag, `dry-run`, builds everything without
releasing anything. Fill in `only` (say `aarch64-apple-darwin`) to build
just some targets while you debug one.

`release.yml` was generated by dist and then edited by hand, so don't
regenerate it with `dist generate`. The top of the file lists the hand
edits.

### Updater signing key

The app's updates are signed, here's the command that made the keys:

```sh
cargo tauri signer generate -w ~/.tauri/patchwork.key
```

Put the public key in `plugins.updater.pubkey` in
`crates/patchwork-gui/tauri.conf.json`. Put the private key's contents and
its password in the repository secrets `TAURI_SIGNING_PRIVATE_KEY` and
`TAURI_SIGNING_PRIVATE_KEY_PASSWORD`. Without the private key we can't update
existing deployments so don't lose it

## AI Use
As with all PRs, AI-assisted/generated PRs will be checked for code quality and coherence with
the existing codebase. If you want to add a large feature, make an Issue for it
so people can discuss implementation details before actually writing the code.
All changes *must* be thoroughly tested before merging.
